# 동행 푸시 알림 후속 작업 계획

## 1. 문서 상태와 목적

- 작성일: 2026-09-15.
- 상태: 작업 계획 작성. 아래 후속 구현과 검증은 미완료 상태다.
- 코드 기준: `feat/205`의 `3f566f0` 커밋.
- 관련 이슈: [#205](https://github.com/TEAM-Nearby/nearby-server/issues/205).
- 기존 PR: [#206](https://github.com/TEAM-Nearby/nearby-server/pull/206), 대상 브랜치 `develop`.
- 선행 설계: [ADR-03 동행 요청 푸시 알림 설계](../architecture/ADR-03-companion-push-notifications.md).

1차 푸시 구현 이후 남은 운영 결함, 알림 목록의 커서 조회, 실제 기기 검증을 실행 가능한 작업으로 나눈다. 기존 커밋을 8개로 분리한 것은 완료했지만, 그 작업이 이 문서의 보완 사항을 구현하거나 운영 전달을 검증한 것은 아니다.

작업 순서는 **기존 PR의 운영 보완 → 별도 PR의 커서 조회 → 스테이징 실기기 검증 → 운영 워커 활성화**로 잡는다. 앱 빌드와 테스트 환경 준비는 서버 구현 중에도 진행할 수 있다. 커서 API 전환 자체가 서버 푸시 발송의 기술적 선행 조건은 아니다.

## 현재 진행 상태

- [x] 커서 페이지 조회 계약·유스케이스·방향별 조회 쿼리·정렬 인덱스의 1차 구현.
- [x] 푸시 작업의 등록 버전 스냅샷과 조건부 토큰 비활성화의 1차 구현.
- [x] 점유 만료 복구 시 최대 시도 횟수와 만료·비활성 정리 배치의 처리량 상한.
- [x] FCM TTL·APNs 만료 시각, 연결·응답·쓰기 타임아웃, `Retry-After` 추출과 오류별 백오프 지연.
- [x] 워커 활성화 시 FCM 프로필·프로젝트 ID를 확인하는 시작 설정 검증.
- [ ] PostgreSQL 실환경 동시성·실행 계획 검증, 상태 기반 지연 알림 생략, 보존·관측 지표, 앱 전환, 실기기 검증.

위 체크 항목은 코드와 단위·H2 기반 회귀 테스트가 반영된 상태를 뜻한다. PostgreSQL과 실제 FCM·기기에서의 결과는 별도 검증이 끝나기 전까지 완료로 처리하지 않는다.

## 2. 현재 구현과 변경 범위

| 구분 | 현재 구현 | 이번 후속 작업 |
| --- | --- | --- |
| 알림 생성 | 업무 트랜잭션에서 알림과 활성 기기별 발송 작업을 저장한다. | 실제 PostgreSQL에서 전체 롤백과 생성 멱등성을 검증한다. |
| 기기 등록 | 사용자·설치 ID의 유니크 제약과 토큰 기반 이전 사용자 비활성화를 사용한다. | 설치·토큰의 활성 소유권, 등록 버전, 동시 등록을 보완한다. |
| 발송 워커 | 배치 선점, 점유 토큰, 재시도, 만료·복구 경로가 있다. | 모든 경로의 시도 횟수 제한과 정리 배치 크기를 보장한다. |
| 토큰 실패 | `UNREGISTERED` 결과에서 기기 ID로 비활성화한다. | 발송 당시 등록 버전·토큰이 현재 등록과 일치할 때만 비활성화한다. |
| FCM 어댑터 | `sendEach`로 발송하며 오류 코드를 결과로 전달한다. | 호출 시간, 재시도 대기 정보, 공급자 유효기간을 반영한다. |
| 실행 설정 | 워커 기본값은 비활성이고, `!fcm` 프로필에서는 로컬 어댑터가 선택된다. | 운영 워커와 실제 발송 어댑터의 조합을 시작 시 검증한다. |
| 알림 목록 | 방향별 조인 쿼리가 전체 목록을 `created_at DESC`로 반환한다. | 기존 경로를 유지하며 커서 페이지 API를 추가한다. |
| DB 테스트 | persistence 모듈의 테스트 의존성에 H2가 있다. | PostgreSQL 전용 쿼리와 동시성을 실제 PostgreSQL에서 검증한다. |

이번 단계에 메시지 브로커 도입, 별도 워커 서비스 분리, 기존 알림 목록의 의미 변경은 포함하지 않는다. 보낸 요청은 현재 구현과 동일하게 수락·거절 결과 알림을 조회하며, 이를 모든 신청의 이력 조회로 확장하지 않는다.

## 3. 변경 위치와 커밋 원칙

| 모듈 | 담당 변경 |
| --- | --- |
| `application` | 등록·발송 정책, 기술 중립적인 포트와 결과 타입, 커서 페이지 유스케이스, 단위 테스트. |
| `adapter-out:persistence` | 원자적 등록, 조건부 갱신, 배치 선점·정리, 마이그레이션, 페이지 쿼리, PostgreSQL 통합 테스트. |
| `adapter-out:notification` | Firebase SDK 설정, 공급자 오류·대기 정보 변환, Android TTL·APNs 만료 설정. |
| `adapter-in:web` | 새 페이지 API, 요청 검증, 응답 DTO, 기존 계약 회귀 테스트, 별도 `*Api` 인터페이스의 Swagger 문서. |
| `bootstrap` | 빈 연결, 워커·정리 스케줄러, 설정 검증, 관측 도구 연결. |

Firebase·JPA 타입은 `application`의 공개 계약에 노출하지 않는다. 업무 정책은 `companion` 기능 내부에 유지한다.

- 기존 8개 커밋은 유지하고 후속 커밋을 추가한다.
- 하나의 동작 변경에 필요한 코드·설정·회귀 테스트를 함께 커밋한다.
- 스키마와 이를 사용하는 코드를 의존 순서대로 배치하고, 각 코드 커밋이 컴파일되도록 한다.
- 이미 적용되었을 수 있는 V21을 수정하지 않고 새 마이그레이션을 추가한다. 버전은 구현 시 브랜치의 최신 번호를 확인한다.
- 사용자 변경과 다른 기능 수정은 포함하지 않는다.

## 4. A단계: 기존 PR #206의 운영 보완

### A0. PostgreSQL 검증 기반

**예정 커밋:** `205 test: 푸시 PostgreSQL 통합 테스트 기반 구성`.

- Testcontainers 기반 PostgreSQL 테스트를 구성하고, 테스트 DB에 실제 Flyway 마이그레이션을 적용한다.
- PostgreSQL 버전은 배포 환경을 확인한 뒤 맞춘다. 로컬 컨테이너 실행 가능 여부와 CI 실행 조건을 확인한다.
- 현재 CI의 `./gradlew test`에서 해당 테스트가 실행되도록 연결한다. 별도 Gradle 작업으로 분리한다면 CI에도 명시적으로 추가한다.
- 업무 요청·기기·알림 생성에 필요한 테스트 데이터와 두 개의 독립 트랜잭션을 실행할 보조 코드를 준비한다.
- 동시성은 래치·배리어로 실행 순서를 제어한다. 임의의 긴 대기로 성공 여부를 판단하지 않는다.

**완료 조건:** 빈 PostgreSQL에 스키마를 구성하고, 실제 저장소 쿼리의 기본 저장·조회 테스트를 실행한다. PostgreSQL 환경이 없어서 실행하지 못한 결과를 H2 통과로 대체하거나 완료 처리하지 않는다.

### A1. 기기 등록 버전과 활성 소유권

**예정 커밋:** `205 fix: 푸시 기기 등록 소유권과 토큰 갱신 경쟁 보완`.

- 기기 등록 버전과 발송 작업의 등록 버전 스냅샷을 추가한다. 동일 등록의 단순 재호출은 멱등하게 처리하고, 토큰·계정 연결이 바뀌면 버전을 변경한다.
- 활성 설치와 활성 토큰의 소유권을 DB 제약으로 보장한다. 새 행이 동시에 생성되는 경우까지 보호하는 원자적 등록 처리를 구현한다.
- 기본 설계 후보는 활성 행의 유니크 제약과 소유권 키별 트랜잭션 직렬화다. 잠금 순서를 일정하게 정하고, 충돌 재시도에는 상한을 둔다.
- 최대 4,096자인 토큰 원문을 그대로 유니크 인덱스 키로 쓰는 방식은 피한다. 고정 길이 토큰 지문을 사용하는 후보를 검토하고 원문 일치도 확인한다. 설치 ID와 토큰의 유효 범위는 현재 지원 앱·Firebase 프로젝트 기준으로 명시한다.
- 토큰 실패에 따른 비활성화는 `endpointId + 등록 버전 + 발송 당시 토큰`을 조건으로 갱신한다. 현재 발송 작업의 점유권을 잃은 결과도 부수 효과를 만들지 못하게 한다.
- 계정 전환 시 이전 연결을 무효화한다. 이전 연결의 대기 작업은 발송 대상 조회에서 즉시 제외하고, 상태 정리는 제한된 배치로 처리한다.
- 기존 활성 소유권 중복의 탐지·해소와 버전 초기화를 마이그레이션 계획에 포함한다.

**완료 조건:** 동일 설치·동일 토큰의 동시 등록, 계정 전환, 토큰 갱신 직후 이전 토큰 실패, 반복 등록을 PostgreSQL 테스트로 재현한다. 새 등록이 과거 응답으로 비활성화되지 않고 활성 소유권 제약이 유지되어야 한다.

### A2. 발송 시도 횟수와 점유·정리 배치

**예정 커밋:** `205 fix: 푸시 선점 복구와 정리 배치의 처리량 제한`.

- 시도 횟수는 작업 선점 시 증가하는 서버 발송 시도 수로 정의한다. Firebase SDK 내부 HTTP 재시도는 별도 호출 시간 예산에 포함한다.
- 선점, 정상 실패, 점유 만료 복구에서 최대 시도 횟수를 적용한다. 워커가 반복 종료되어도 무한 복구하지 않는다.
- 유효기간이 지난 작업은 만료 처리하고, 시도 횟수를 소진한 작업은 종료 사유를 기록한다. 두 조건이 함께 만족될 때의 우선순위도 테스트로 고정한다.
- 만료·복구·비활성 작업 정리는 각각 제한된 건수와 짧은 트랜잭션으로 실행한다. PostgreSQL에서 제한된 ID를 잠금·조회하고 갱신하는 방식으로 구현한다.
- 결과 반영은 현재 점유 토큰에 한정한다. 외부 FCM 호출 동안 DB 행 잠금을 유지하지 않는다.

**완료 조건:** 두 워커의 중복 선점 방지, 마지막 시도 중 워커 종료, 만료 작업 복구 방지, 이전 워커의 늦은 결과 차단, 정리 건수 상한을 검증한다.

### A3. FCM 호출 시간과 오류별 재시도

**예정 커밋:** `205 fix: FCM 호출 시간과 오류별 재시도 정책 보완`.

- 사용 중인 Firebase Admin SDK에서 연결·응답 타임아웃, 내부 재시도, `sendEach`의 배치 처리 시간이 어떻게 적용되는지 확인한다.
- 점유 시간은 개별 HTTP 타임아웃뿐 아니라 내부 재시도와 배치 처리 상한, 결과 저장 여유를 포함해 정한다. 취소 후에도 외부 전송이 계속될 수 있는 경로를 확인한다.
- 단순히 호출 스레드의 대기만 중단하고 전송이 취소되었다고 처리하지 않는다. 시간 상한을 보장하기 어려우면 배치 크기·전송 방식 또는 점유 연장 전략을 조정하고 근거를 기록한다.
- `PushDeliveryResult`에 공급자 재시도 가능 시각 등 기술 중립적인 정보를 전달하도록 확장한다. 전체 호출 예외와 기기별 실패에 같은 오류 분류를 적용한다.
- 지수 백오프와 무작위 지연을 적용하되 공급자 대기 지시와 오류별 최소 지연보다 빨리 재시도하지 않는다. SDK가 해당 정보를 노출하는지 확인하고 누락 시 적용할 대체 정책도 테스트한다.
- 메시지·토픽 전송률 할당량 오류의 최소 초기 지연 1분, `UNAVAILABLE`의 `Retry-After` 준수는 [FCM 오류 처리 문서](https://firebase.google.com/docs/cloud-messaging/error-codes)를 기준으로 한다.

**완료 조건:** 429·503·영구 실패·전체 호출 예외·대기 지시 누락·지연 응답을 통제 가능한 테스트로 확인한다. 시간과 난수는 주입해 경계값을 재현하고, 실제 Firebase 장애 발생을 테스트 조건으로 삼지 않는다.

### A4. 유효기간과 최신 업무 상태

**예정 커밋:** `205 feat: 푸시 유효기간과 지연 알림 생략 정책 적용`.

- `PushMessage`에 만료 정보를 전달하고, FCM 호출 직전 남은 유효기간을 계산한다.
- 만료된 메시지는 전송하지 않는다. 남은 시간을 Android TTL과 APNs 만료 시각에 반영한다. 플랫폼별 표현은 [FCM 메시지 유효기간 문서](https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-lifespan)를 따른다.
- 신청 도착 알림은 발송 직전 현재 신청 상태를 조회해 이미 수락·거절된 경우 생략한다. 배치 상태 조회로 건별 추가 쿼리를 줄인다.
- 결과 알림은 설정된 유효기간 동안 전달한다. 활성 기기에는 모두 전송하고, 등록 기기가 없으면 알림함 기록으로 확인한다.
- 푸시 접수·수신으로 읽음 상태를 변경하지 않는다.

**완료 조건:** 만료 직전·직후, 상태 확인 전에 처리된 신청, 결과 알림, 기기 미등록, 읽음 상태 유지, 플랫폼별 만료 필드를 검증한다.

발송 직전 확인과 외부 전송 사이에도 업무 상태가 바뀔 수 있다. 이미 공급자에 접수된 푸시는 회수할 수 있다는 전제를 두지 않는다. 앱은 클릭 후 서버에서 최신 상태와 현재 계정의 접근 권한을 다시 확인한다.

### A5. 실행 설정·보존·관측

**예정 커밋:** `205 feat: 푸시 운영 설정 검증과 보존 및 관측 추가`.

- 실제 배포 환경을 구분하는 설정을 확인하고, 운영 워커가 켜졌을 때 실제 FCM 어댑터·프로젝트·인증 설정을 사용하도록 검증한다. 잘못된 조합은 시작 시 실패시킨다.
- 로컬 어댑터는 개발·테스트 용도를 명시한다. 운영 워커 기본 비활성 설정은 유지한다.

- 대기 작업의 최대 대기 시간, 접수 지연, 재시도·영구 실패·만료·생략 건수, 정리 건수와 실행 시간을 수집한다.
- 사용자·알림 ID·토큰을 메트릭 라벨로 사용하지 않는다. 추적 로그에는 필요한 식별자와 종료 사유를 남기되 토큰·인증 원문은 남기지 않는다.

**완료 조건:** 운영 설정 조합별 시작 성공·실패, 보존 경계값과 삭제 상한, 미완료 작업 보존, 지표 증가를 검증한다.

## 5. B단계: 별도 PR의 커서 조회

### API 계약과 호환성

기존 `GET /api/users/me/companion-requests?direction=...`의 전체 조회 계약은 유지한다. 새 API 경로는 다음으로 계획한다.

```http
GET /api/users/me/companion-requests/page?direction=RECEIVED&size=20&cursor=...
```

현재 `CommonResponse` 외곽 구조를 유지하고, 내부 응답 데이터에 페이지 정보를 추가한다. 아래는 내부 데이터 예시이며 커서 문자열은 설명용이다.

```json
{
  "direction": "RECEIVED",
  "requests": [],
  "nextCursor": null,
  "hasNext": false
}
```

- 정렬은 `notification.created_at DESC, notification.id DESC`다.
- 첫 페이지는 커서를 생략한다. 다음 페이지는 마지막 반환 알림의 `(created_at, id)`보다 작은 항목을 조회한다.
- 크기는 기본 20, 허용 범위 1~100이다. 범위를 벗어나면 입력 오류로 처리한다.
- `size + 1`개를 조회해 `hasNext`를 결정하고 초과 한 건은 응답에서 제외한다. 다음 페이지가 없으면 `nextCursor`는 `null`이다.
- 커서는 버전·UTC 생성 시각·알림 ID·방향을 포함한다. Base64url로 인코딩한 불투명 문자열로 제공하고 길이·형식·값·버전·방향을 검증한다. 인코딩을 인증이나 위변조 방지 수단으로 취급하지 않는다.
- 사용자 ID는 인증 정보에서만 가져온다. 타 사용자 커서를 재사용해도 현재 사용자 범위를 벗어나지 않아야 한다.
- DB 저장 시각의 정밀도를 커서 왕복 과정에서 보존한다. 정렬 필드는 변경하지 않는다.
- 페이지 사이 신규 알림은 이후 페이지에 섞이지 않으며, 첫 페이지 새로고침으로 확인한다. 여러 페이지 전체에 대한 DB 스냅샷 일관성을 제공하지는 않는다.

### 커밋 순서와 검증

| 순서 | 커밋 범위 | 완료 조건 |
| --- | --- | --- |
| B1 | 커서 값·검증, 페이지 결과와 조회 포트, 유스케이스. | 동일 시각의 ID 순서, 잘못된 커서·크기·방향·버전, 빈 페이지·마지막 페이지를 테스트한다. |
| B2 | 방향별 PostgreSQL 페이지 쿼리, 필요한 조회 필드, 인덱스 마이그레이션. | 사용자 범위, 페이지 사이 삽입, 조인으로 인한 중복 행 여부, 실제 실행 계획을 검증한다. |
| B3 | 페이지 컨트롤러·Swagger·응답 DTO, 앱 전환 문서. | 기존 전체 조회 계약과 새 API의 응답·입력 오류·인증 동작을 검증한다. |

인덱스의 기본 후보는 `(recipient_user_id, created_at DESC, id DESC)`다. 기존 인덱스와 중복 비용을 비교하고 `SENT`·`RECEIVED` 각각의 실제 조인 쿼리로 확정한다. 알림 하나가 조인 결과 여러 행으로 늘어나면 페이지 제한 전에 해결한다.

대표 데이터는 사용자당 알림 20건·1,000건·100,000건과 방향별 편중, 동일 생성 시각을 포함하도록 준비한다. 첫 페이지와 깊은 페이지에서 `EXPLAIN (ANALYZE, BUFFERS)` 결과, 스캔 행 수, 정렬·버퍼 사용량, 실행 시간을 기록한다. 반환 건수 제한만으로 DB 조회 비용이 제한되었다고 판단하지 않는다.

**B단계 완료 조건:** API·조회·호환성 테스트와 PostgreSQL 실행 계획 기록이 있다. 앱의 페이지 조회 전환 확인 전에는 기존 API를 제거하지 않는다. 신규 PR의 브랜치·이슈 번호는 생성 시 정하며, 기존 PR 번호를 임의로 재사용하지 않는다.

## 6. C단계: 스테이징과 실제 기기 검증

### 준비할 환경과 담당 범위

| 준비 항목 | 작업 범위 | 현재 상태 |
| --- | --- | --- |
| 테스트 Firebase 프로젝트·서버 인증·스테이징 DB. | 서버에서 환경 연결을 검증한다. 프로젝트와 권한 제공은 해당 환경 소유자의 협조가 필요하다. | 접근 가능 여부 확인 필요. |
| 푸시 연동 앱 빌드. | 앱에서 등록·갱신·로그아웃, 수신 처리, 상세 진입을 구현하고 빌드를 제공한다. | 지원 플랫폼과 빌드 확인 필요. |
| 실제 Android·iOS 기기. | 지원 플랫폼별로 수신·표시·클릭 시나리오를 실행한다. | 기기 접근 가능 여부 확인 필요. |
| iOS APNs 설정. | iOS 지원 시 Firebase 프로젝트에 연결된 설정과 앱 환경을 확인한다. | iOS 지원 여부에 따라 필요. |
| 시나리오·추적 로그·테스트 사용자 A/B. | 서버 작업에서 준비하고 앱 검증 결과와 연결한다. | 작성·준비 예정. |

이 환경이 준비되지 않아도 A·B단계의 서버 구현과 자동화 검증은 진행한다. 실제 기기 접근이나 앱 빌드가 없으면 C단계의 해당 결과를 미검증으로 남긴다.

### 실기기 시나리오

테스트 사용자 A가 B에게 신청하고, B가 수락·거절하는 흐름을 지원 플랫폼별로 실행한다.

| 시나리오 | 확인할 결과 |
| --- | --- |
| 앱 전경. | 수신 처리, 배너 정책, 알림 목록 갱신이 동작한다. |
| 앱 백그라운드·일반 종료 후 진입. | 플랫폼 조건에 맞게 시스템 알림이 표시되고 클릭 시 올바른 요청으로 이동한다. 강제 중지 상태는 별도 조건으로 기록한다. |
| 알림 권한 거부. | 푸시 표시 여부와 무관하게 알림함을 조회할 수 있다. |
| 오프라인 후 재연결. | 유효기간이 적용되고 상세 화면은 최신 업무 상태를 보여준다. |
| 로그아웃·계정 전환·토큰 갱신. | 이전 연결의 신규 전송을 차단하고 이전 계정의 상세 내용에 접근하지 못한다. 이미 접수된 푸시의 표시 여부도 별도로 기록한다. |
| 같은 알림 재수신. | `notificationId` 기준으로 목록 중복과 과거 상태 덮어쓰기를 막는다. 시스템 배너의 중복 표시 여부도 별도 기록한다. |
| 복수 기기 중 일부 실패. | 정상 기기는 수신하고 실패 작업만 재시도한다. |

### 결과 기록 양식

각 시나리오는 아래 필드를 채워 기록한다. 여러 기기의 발송 작업을 구분하기 위해 `notificationId`와 `deliveryId`를 함께 사용한다.

| 필드 | 기록 내용 |
| --- | --- |
| 실행 환경. | 날짜, 서버 커밋, 앱 빌드, OS·기기, 전경·백그라운드 상태, 권한·네트워크 조건. |
| 추적 정보. | `notificationId`, `deliveryId`, 시도 횟수, DB 최종 상태·종료 사유. |
| FCM 접수. | 접수 성공·실패, 공급자 메시지 ID 또는 오류, 접수 시각. |
| 기기 결과. | 수신·표시 여부와 시각, 중복 여부, 클릭 후 화면·계정·권한 결과. |
| 판정. | 성공·실패·미실행, 증거 위치, 재현 절차, 후속 수정 항목. |

**C단계 완료 조건:** 지원 플랫폼의 필수 시나리오가 실제 기기에서 확인되고, 실패 항목 수정 후 재검증한 기록이 있다. DB `SENT`는 공급자 접수 결과이며 기기 표시·사용자 읽음을 의미하지 않는다. 외부 전송과 DB 기록은 단일 트랜잭션이 아니므로 정확히 한 번 전달을 보장한다고 보고하지 않는다.

## 8. 출시와 장애 시 대응

1. 운영 보완 PR과 관련 검증 결과를 검토한다. 워커가 비활성인 상태에서 마이그레이션과 새 코드의 호환성을 확인한다.
2. 커서 API는 추가 제공하고 앱을 전환한다. 기존 전체 조회 경로의 정리는 별도 변경으로 수행한다.
3. 스테이징에서 FCM 연동과 실제 기기 시나리오를 실행한다. 운영 적용값과 관측 기준을 기록한다.
4. 운영 활성화 시점의 누적 작업과 유효기간을 확인하고, 허용된 초기 처리량으로 워커를 켠다.
5. 발송 지연·오류·DB 부하를 관찰한다. 문제가 생기면 워커를 비활성화해 추가 선점을 중단하고 원인을 조사한다.

현재 설정이 시작 시 읽히는 방식이면 비활성화에도 애플리케이션 재시작이 필요하다. 이미 진행 중이거나 FCM에 접수된 전송이 즉시 취소된다고 가정하지 않는다. 종료 작업을 무조건 재활성화하거나 누적 작업을 일괄 재전송하지 않는다. 롤백은 추가 스키마와 구버전 코드의 호환성을 확인한 버전으로 수행하며 데이터를 삭제해 되돌리지 않는다.

이 문서의 작성은 PR 머지·스테이징 배포·운영 활성화의 실행 결과를 의미하지 않는다. 각 단계는 코드 검증, CI, 환경 배포, 실제 기기 결과를 구분해 완료 처리한다.
